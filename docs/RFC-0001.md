# RFC-0001: PostgreSQL Workspaces for AI Agents

## Implementation architecture and production delivery plan

**Status:** Proposed; implementation and benchmark gates remain open.  
**Revision:** 0.3 — 19 September 2026.  
**Revision focus:** Recovery, offline expiry, authorization after management restore, source WAL protection, policy transitions, and enforceable lifecycle/lineage contracts. The classifier remains untrained.  
**Working name:** PG Workspaces (PGWS); not a branding decision.  
**Audience:** Founders, database engineers, infrastructure engineers, and security reviewers.  
**Implementation baseline:** The supplied `pg-workspace-poc.zip`, reviewed and unit-tested for this RFC.  
**License proposal:** Apache-2.0 for project-owned code, including the management and isolation components. Upstream dependencies retain their own licenses.

### Decision requested

Build a PostgreSQL workspace service, not a new database engine. Maintain one continuously updated baseline for each approved source/privacy profile, then provision isolated writable workspaces using copy-on-write storage. Keep normal PostgreSQL SQL, drivers, and application migration tools. Make workspace creation, freshness, lifecycle, and permissions explicit through an API and CLI.

Use PostgreSQL 18, Linux, OpenZFS, and isolated PostgreSQL instances for the first implementation. Use a Go control plane and host agent; preserve the Python POC as a regression and experimental harness. Start with self-managed sources and dedicated-tenant infrastructure. Add continuous sanitized ingestion as a separately qualified connector, not an implicit capability of physical cloning.

For privacy discovery, train a project-owned tiny column classifier from scratch. The initial design uses 24 semantic classes, approximately 1.5 MiB of FP32 weights, and local Go inference. It proposes transformations through a policy compiler; it cannot authorize raw copying. Sections 10.7–10.15 define the training, evaluation, runtime and rollout contract. No pretrained or hosted model is required.

**The first production service is a reliable service for disposable development/test databases. It is not initially a replacement for the customer's production primary, an automatic database merge system, or a zero-loss managed database service.**

### Evidence and interpretation

Statements marked as proposed requirements describe the system to be built. Performance figures are targets or planning inputs, not measurements. References [1]–[35] are retained from revision 0.1; [36]–[45] support the classifier addition and were checked for revision 0.2. [P0] identifies the supplied local POC. Where a dependency cannot establish the required behavior, this RFC requires an experiment or implementation change before release.

Evidence and unexecuted acceptance gates are recorded separately in VALIDATION.md. No result in this RFC should be read as a passed production acceptance test.

## 1. Product contract and scope

### 1.1 The unit of value

A workspace is a task-scoped PostgreSQL environment containing an approved version of a source database. An agent receives a standard connection endpoint and limited credentials. It can run application queries, modify data, apply supported migrations, and run tests without changing production or another workspace.

A workspace is pinned to a source generation and a particular captured state. It is not a moving replica after it becomes writable. Agents working on the same task may share one workspace; the product does not require one permanent database per agent identity.

The primary workflow is: register source; prepare baseline once; continuously ingest changes; create task workspace; apply migration artifacts and tests; publish test results; expire workspace. A subsequent production deployment is performed by the customer's existing deployment system.

### 1.2 Release boundaries

| Release | Included | Explicitly excluded |
| --- | --- | --- |
| P0: verified laboratory | Existing fixture; recovery tests; storage and memory benchmarks | Real customer data; availability claims |
| P1: self-hosted alpha | Approved PostgreSQL 18 physical sources; HTTP API/CLI; isolated workspaces; quotas; TTL; explicit resume/reset | Arbitrary managed sources; privacy claims; cross-tenant shared hosts |
| P2: hosted private beta | Dedicated tenant VM/host cells; TLS; identity; audit; metering; support runbooks | Hostile tenants sharing a kernel; automatic production promotion |
| P3: sanitized connector | Narrow logical/DDL matrix; transaction-safe transformations; policy versioning; self-trained local discovery classifier with review gates | Universal anonymization; arbitrary DDL; model-authorized raw copying |
| Later RFC | Durable retained databases, more sources, regional distribution, optional connection-triggered resume | No commitments in this RFC |

These are acceptance-based stages, not promises of completion dates. P3 development can run in parallel with P1/P2, but no sanitized workspace is exposed before its independent release gates pass.

### 1.3 Non-goals

No new query language, generic vector-memory platform, distributed SQL engine, automatic branch merging, automatic production deployment, browser/mobile offline synchronization, arbitrary native extensions, or transparent live rebasing. Ordinary websites and mobile applications can use a workspace through their backend; direct end-user database authorization is outside the initial product.

No repeated full import for ordinary source transactions or workspace creation. Supported physical source migrations flow through WAL. Sanitized schema changes that alter the approved plan follow the explicit generation transition in section 10.6 and can require a new load. Reinitialization remains an explicit operation for lost WAL, incompatible source upgrades, policy rebuilds, or unrecoverable ingestion state.

## 2. Review of the supplied POC

### 2.1 Artifact and observed validation

The reviewed archive is `pg-workspace-poc.zip`, SHA-256:

```text
b13adbe98285ac0fa49d58c3232fc0e4375b8c97d37eee466fdc528db7fd2f48
```

The archive contains `pgws.py`, a README, a validation record, two shell scripts, an example migration, and unit tests. The controller is approximately 42 KB of Python. `python3 -m unittest discover -s tests -v` completed with 33 passing tests during this RFC review. The recorded test output is included in the companion package. [P0]

The POC already distinguishes the initial physical copy from subsequent snapshot/clone operations. Its `Controller.create` path captures a lower-bound LSN, snapshots the live baseline, creates a clone, recovers it as a disconnected standby, promotes the clone, changes credentials, and only then opens application access. Its source and replica are synthetic instances on the same host. [P0]

### 2.2 What to retain and replace

| Area | Existing evidence | Implementation action |
| --- | --- | --- |
| Replication and branch sequence | Code and mocked tests, not a live validation | Retain the conceptual sequence; qualify with actual PostgreSQL/ZFS tests |
| Configuration | Fixture uses compatible small settings everywhere | Add source discovery and separate recovery/runtime profiles |
| State | Local JSON file and process lock | Replace with durable operations, generations, reconciliation, and fencing |
| Network | Internal Docker networks and loopback ports | Add TLS, dedicated tenant boundaries, egress controls, and revocation |
| Lifecycle | Create, stop, start, delete | Add TTL, idempotency, reset semantics, and orphan cleanup |
| Capacity | Container limits and reporting | Add scheduler admission, storage budgets, pool-pressure protection |
| Privacy | Sanitization requests explicitly rejected | Preserve fail-closed behavior until a qualified logical pipeline exists |
| Validation | 33 passing unit tests | Add mandatory integration, crash, security, and workload gates |

The controller's `configure` method deliberately assumes known fixture roles and overwrites several source settings. That is acceptable for the fixture, not for an arbitrary production source. A real source can have different owners, high connection settings, extensions, subscriptions, external tablespaces, and background jobs. The alpha must inventory or reject these conditions rather than quietly copy the fixture defaults. [P0]

### 2.3 Important sizing correction

Some hot-standby shared-memory settings must be at least as large as the primary's during recovery: `max_connections`, `max_prepared_transactions`, `max_locks_per_transaction`, `max_wal_senders`, and `max_worker_processes`. An incompatible increase on the source can pause or stop replay. [3]

Consequently, a nominal 1 GiB workspace profile is not automatically a valid recovery profile for every source. The implementation MUST discover recovery requirements, reserve startup capacity, and either recover with a larger temporary profile or reject the source/profile combination. After promotion, a controlled restart may apply a smaller steady-state configuration. This adjustment adds latency and must be measured.

## 3. Terminology and non-negotiable invariants

### 3.1 Terms

**Source:** The external PostgreSQL system from which state is ingested. **Source epoch:** A service-controlled lineage generation used to invalidate incompatible freshness tokens. **Baseline:** A continuously updated, non-agent-writable PostgreSQL instance. **Baseline generation:** An immutable identity for a particular initialized baseline and its compatibility/privacy contract.

**Snapshot:** An immutable storage capture. **Workspace generation:** One physical realization of a workspace identity; reset replaces the generation. **Freshness token:** A signed reference to a source epoch, system identifier, timeline, and required WAL position. **Ready:** Recovery, isolation, authentication, and endpoint checks have all completed.

**Sanitized baseline:** A clean database populated by approved transformations. This term does not assert legal anonymity. **Cell:** One tenant-dedicated compute/storage failure domain in the initial hosted design.

### 3.2 Required invariants

| ID | Requirement |
| --- | --- |
| I-01 | An exposed workspace has no ability to replicate from or write to the source. |
| I-02 | Workspace writes cannot modify a baseline, another workspace, or management metadata. |
| I-03 | A ready workspace satisfies its recorded freshness lower bound within the verified source lineage. |
| I-04 | A snapshot, runtime image, source epoch, and privacy-policy hash are recorded before exposure. |
| I-05 | Sanitized access cannot be downgraded to raw access by agent-supplied parameters. |
| I-06 | Source credentials and current service authorization are not inherited as usable workspace authority. |
| I-07 | Retried lifecycle requests do not create duplicate resources or repeat destructive operations unexpectedly. |
| I-08 | Every destructive operation checks tenant, object identity, generation, and fencing token. |
| I-09 | Committed metadata never asserts readiness solely because a container exists or a TCP port opens. |
| I-10 | Storage sharing never crosses tenant/privacy boundaries chosen by the service. |
| I-11 | Source safety takes priority over workspace freshness; source WAL retention is bounded. |
| I-12 | Missing WAL, unsupported schema changes, uncertain privacy, and ambiguous lineage fail closed. |
| I-13 | Classification is a proposal, never raw-data authorization; unqualified or unknown fields cannot silently pass through. |
| I-14 | Models run only in trusted discovery; initial-load/CDC transformations and branch creation do not perform classifier inference. |
| I-15 | The host closes SQL access at workspace expiry or serving-lease expiry even without the control plane. |
| I-16 | Management restore cannot resume issuance or publication until a new authority epoch and explicit authorization reconciliation are complete. |
| I-17 | A snapshot has the same source lineage and privacy-policy identity as its immutable baseline generation. |

A source migration arriving through replication is not a migration file. The database preserves schema and migration-history tables; the repository preserves migration artifacts. The service records both but does not infer one from the other.

## 4. Reference architecture

### 4.1 Components and trust boundaries

```text
Agent / developer / CI
    | HTTPS lifecycle API                  | PostgreSQL + TLS
    v                                      v
Control plane                         Workspace endpoint
    | durable operation                      |
    v                                        v
Tenant cell host agent ----> isolated PostgreSQL workspace
    | privileged local helper                 |
    +----> OpenZFS baseline snapshot / writable clone
    |
    +----> baseline ingestion ----TLS----> approved source

Separate management PostgreSQL:
identity, sources, policies, operations, routing, audit, usage
```

The control plane MUST use a separate management database, never the customer baseline. It authorizes requests, stores desired state, schedules operations, and publishes status. The host agent reconciles that desired state with real PostgreSQL processes, datasets, and network rules.

A small privileged helper performs only validated storage/runtime operations. The public API has no Docker socket, pool device access, or arbitrary host shell endpoint. The database runtime has no management socket, source credentials, or mount of the baseline directory.

For the first hosted service, each tenant receives a dedicated VM or physical cell. Containers separate that tenant's workspace processes inside the cell. Do not describe namespaces alone as a hostile cross-tenant boundary: Docker's daemon and underlying host remain security-sensitive components. [20]

### 4.2 Technology choices

| Component | Proposed implementation | Reason and constraint |
| --- | --- | --- |
| API, scheduler, CLI | Go; versioned HTTP/JSON contracts | Small operational surface; one codebase for lifecycle logic |
| PostgreSQL access | `pgx`/`pgxpool`; parameterized queries | Existing PostgreSQL driver/toolkit, not a new wire implementation [27] |
| Durable operations | Management PostgreSQL tables and workers | Avoid an initial dependency on Kafka, Redis, or a workflow service |
| Host agent | Go daemon, systemd, authenticated control channel | Host discovery, journal, fencing, reconciliation |
| Storage | OpenZFS on a pinned Linux/kernel combination | Native snapshot/clone and incremental-send primitives |
| Runtime | Pinned OCI image; private container runtime API | One instance per workspace; no customer-chosen images initially |
| Telemetry | Structured logs, metrics, trace IDs | Keep customer values and credentials out of default telemetry |
| Sanitized ingestion | Adapter evaluated against pgstream | Candidate, not an assumed transaction-correct implementation |

Choose exact versions and image digests in a release manifest after compatibility testing. PostgreSQL 18 is the supported major in this RFC; do not depend on a floating image tag or silently upgrade a running physical lineage.

### 4.3 Why not introduce Kubernetes or a new storage engine immediately?

The initial difficult problems are recovery correctness, isolation, ingestion, and lifecycle races. A single well-defined cell is easier to qualify than a scheduler that can move state anywhere. Kubernetes may later operate the control plane or cells, but it does not itself make a local snapshot remotely shareable.

A branch-aware distributed storage service could eventually reduce startup and placement constraints. Building it now would introduce WAL persistence, remote-page reads, garbage collection, recovery, and distributed durability before establishing product demand. The storage interface below deliberately leaves room for another backend without pretending all backends have the same guarantees.

## 5. Compatibility and source onboarding

### 5.1 Physical connector contract

The first connector supports an approved self-managed PostgreSQL 18 cluster, compatible CPU architecture, standard persistent application tables, and an allowlisted runtime/extension set. Physical replication is cluster-wide, not a selective per-table export. Physical replication across major versions is not generally supported; upstream advises keeping primary and standby release levels aligned. [1]

All non-system databases in the source cluster MUST belong to the same authorized tenant. The API may expose only a selected application database, but unrelated databases still exist in the raw physical copy. Reject mixed-tenant clusters unless the entire cluster is explicitly authorized for the same security domain.

P1 rejects external tablespaces/WAL directories, unapproved C extensions, logical subscriptions, outbound FDWs, scheduled database jobs, and prepared transactions. Unlogged table contents are not replicated to a standby; a source with required unlogged application data must be rejected or use an explicitly documented fixture treatment. [22]

Do not advertise managed-provider support until that provider's actual permissions and replication protocol have passed onboarding and failover tests. A service offering a vendor-managed read replica does not by itself establish that an external client can run this connector.

### 5.2 Discovery manifest

Onboarding records server version, system identifier, timeline, WAL segment size, relevant recovery settings, encoding/collations, database inventory, table persistence, tablespaces, extensions and versions, subscriptions, foreign servers, role graph, ownership, and relevant background workers. Discover identifiers through replication/admin interfaces and record the provenance of each value. `IDENTIFY_SYSTEM` exposes system/timeline information; `pg_controldata` provides local cluster-control information. [4][34]

The result is a typed compatibility report with `supported`, `unsupported`, and `requires_review` findings. Lack of permission to inspect an important property is not evidence that the property is safe. Source configuration changes that invalidate the manifest block new workspace creation until reviewed.

Two source identities are proposed: a dedicated replication role and a narrowly scoped inspection role. The customer's administrator installs/grants the required rights; workspace agents cannot use either role. Replication access exposes sensitive cluster state and must be treated as privileged access. [1]

### 5.3 Network and credentials

The source endpoint is registered by a tenant administrator, not supplied afresh with each agent request. The connector verifies TLS hostname and certificate authority. PostgreSQL clients should use `sslmode=verify-full` for this mode; merely requesting encryption is not equivalent to hostname verification. [26]

Use approved egress destinations, bounded DNS resolution, and a private tunnel where required. Block cloud metadata endpoints, management networks, and unapproved address changes. Private source networks are supported through administrator-approved routing, not a blanket exemption from destination validation.

Store source secrets in the service's secret adapter. Mount the active passfile outside every snapshotted dataset. Never put passwords into command-line arguments, metadata JSON, error details, or exported benchmark reports. Rotation changes the active secret reference; it does not require reseeding the database.

## 6. Initial synchronization and continuous physical ingestion

### 6.1 Initial synchronization

Create a new baseline generation and dataset. Allocate a uniquely named replication slot owned by this connector. Provision a pinned runtime and source-compatible recovery settings. Run `pg_basebackup` once with WAL streaming, a controlled transfer rate, and a backup manifest. `pg_basebackup` creates a cluster backup suitable for initializing a standby; it is not a workspace-creation operation. [2]

An illustrative command shape is:

```bash
# PG service/passfile are mounted secrets outside the dataset.
# The controller already created and recorded the slot.
pg_basebackup \
  --dbname='service=approved_source' \
  --pgdata=/srv/pgws/baselines/GEN/pgdata \
  --format=plain --wal-method=stream \
  --slot=pgws_SLOT --checkpoint=spread \
  --manifest-checksums=SHA256
```

The actual agent supplies generated paths and identifiers through validated arguments, not a shell interpolation template. Interrupted initialization is recorded as an incomplete generation; never start PostgreSQL from an arbitrary partially populated directory.

Verify the backup before starting or modifying it. `pg_verifybackup` checks the manifest and necessary WAL, but its documentation explicitly says that verification is not a substitute for a real restore test. [5] After verification, install service-owned configuration and external secret mounts, then start the baseline as a standby.

### 6.2 Ongoing replication

In steady state, maintain one upstream stream per baseline, not one per workspace. Agents never query the baseline. Its only ordinary SQL traffic is bounded health/compatibility inspection. Do not put the baseline in the customer's synchronous-commit path; source transaction latency must not depend on workspace availability.

The connector tracks received, flushed, and replayed WAL positions, source epoch, timeline, and observation time. Monitor slot restart position, active state, retention availability, and invalidation information through `pg_replication_slots`. [21] A stopped WAL receiver or a stale observation is a first-class unhealthy condition. The service does not label an idle database stale merely because its last replayed transaction timestamp is old.

Source migrations affecting ordinary logged state flow through the physical path. A migration that changes the compatibility contract, such as installing an unsupported extension, does not become supported simply because its catalog changes were replicated.

### 6.3 Retention and source protection

A replication slot can retain substantial source WAL. Prefer sacrificing this baseline's recoverability to exhausting production disk. `max_slot_wal_keep_size` is a server-wide setting evaluated at checkpoint time; it is not an immediate per-slot quota. A change can invalidate other consumers' slots. Onboarding MUST inventory existing slots, record the administrator-approved server setting and checkpoint configuration, and prohibit PGWS from silently lowering that setting. [6]

Assign a separate operational WAL budget to each PGWS slot. Size source free-space headroom for peak WAL generation during the measured checkpoint/reaction interval, concurrent source consumers, and an emergency margin. A source-side watchdog operated by the customer, or an equivalent independently qualified mechanism, MUST remain available when the PGWS cell and control plane are unreachable. It checks the recorded PGWS slot identity and follows the approved disconnect/release runbook before the source emergency threshold. Server retention limits are a backstop; they do not replace this monitor. If the source cannot provide the required protection and inspection permissions, reject onboarding for the production connector.

Record peak WAL rate, usable disk headroom, warning/release thresholds, watchdog interval, responsible operator, and affected non-PGWS slots in the onboarding report. Test a WAL burst between checkpoints and total PGWS unavailability. Never promise a strict production disk bound from checkpoint-based retention settings alone.

Proposed policy: alert before 50% of the source-approved WAL budget, stop admitting fresh workspaces when ingestion is unhealthy, and execute the customer's approved slot-release runbook before production disk reaches its emergency boundary. Never drop a slot whose recorded ownership/identity does not match this source connector.

Set `hot_standby_feedback=off` initially and do not run long analytical queries on the baseline. This is a design choice to avoid deliberately prolonging source row-version retention for a development feature. The tradeoff is cancellation of conflicting baseline inspection queries, which must be retried outside the critical capture operation.

### 6.4 Source failover and reseeding

An endpoint change is not enough evidence that a replica can continue. Verify system identity and timeline ancestry. P1 blocks creation on a timeline transition until the connector verifies a supported continuation. Any incompatible reseed creates a new source epoch and baseline generation. A verified continuation onto another timeline also requires a new immutable baseline generation before capture; it cannot rewrite the lineage of the previous generation. Reuse of the existing ingestion storage needs explicit host-journal adoption and connector qualification; otherwise reseed. Existing workspaces remain independent, with their old lineage recorded.

Freshness tokens from another epoch are rejected. Do not compare bare hexadecimal LSNs from unrelated systems or timelines and declare them ordered. A later connector may accept verified ancestor tokens after failover; this is not required for P1.

## 7. Freshness contract

### 7.1 Three modes

| Mode | Meaning | Failure behavior |
| --- | --- | --- |
| `snapshot` | Use an authorized immutable snapshot ID | Fail if unavailable or policy-revoked |
| `latest` | Capture a source barrier when the request is processed; include at least it | Fail on unreachable source or deadline; no silent stale fallback |
| `at_least` | Include the supplied signed barrier token | Reject wrong lineage; wait for replay or fail |

An explicit `allow_stale_snapshot` option may later request an existing approved capture. It must never be an undocumented fallback for `latest`.

The guarantee is a lower bound, not an exact historical cut: a workspace can contain later transactions already present in the captured WAL. It must not omit required committed changes. Exact point-in-time branching is a separate recovery feature.

### 7.2 Obtaining a durable barrier

For a physical deployment barrier, the caller finishes its migration transaction before requesting the token. The connector samples `pg_current_wal_insert_lsn()`, then waits until `pg_current_wal_flush_lsn()` reaches that sample. Only afterward does it sign the source identity/epoch/timeline and required position. This proposed procedure avoids confusing an inserted record with a durably flushed one; PostgreSQL exposes separate insertion, write, and flush positions. [7]

The caller must not request a barrier concurrently and assume it includes a transaction that has not committed yet. Independent sessions require application-level ordering. Source identity is checked before and after token issuance; an observed lineage change retries or fails issuance.

For the logical connector, use a committed marker in a service-owned published relation. Decode its source commit boundary, sign that boundary, and require the marker plus all preceding eligible transactions to be durably applied to the clean target. Grant only bounded marker-writing rights to the barrier role. This avoids waiting for an arbitrary physical WAL position that produces no published row event. Marker retention and cleanup are part of the connector. Qualify idle-source barriers explicitly; do not treat a receiver keepalive as proof of target apply.

### 7.3 Checking the capture

Before a physical snapshot, require baseline replay to reach the token position. After cloning, independently verify recovery reached at least that position before exposure. Store both the requested position and the recovered source position. Record snapshot GUID and lineage; timestamps alone are not correctness evidence.

For a sanitized baseline, source and target WAL positions are different coordinates. Use the target's durable applied-source journal to prove that the required source transaction boundary has been materialized. Never compare a source LSN directly with the sanitized database's own WAL position.

## 8. Workspace creation and recovery algorithm

### 8.1 State and admission

The API validates authorization, baseline/privacy eligibility, TTL, requested resource profile, and idempotency. In one management transaction it creates the workspace, reserves initial capacity, and records an operation. The response is `202 Accepted` with workspace and operation IDs; it contains no database password.

The worker obtains a lease and monotonically increasing fencing token. Host admission reserves steady-state capacity plus temporary recovery memory and an I/O startup slot. Initial proposed limits are two concurrent recovery starts per cell and bounded per-project queue depth; benchmark these rather than assuming 14 simultaneous starts are harmless.

### 8.2 Physical-standby baseline sequence

1. Resolve and persist the freshness barrier and compatibility manifest. Confirm the baseline is healthy and eligible under current policy.
2. Create an immutable snapshot containing the complete approved cluster storage, including WAL. Record and hold its GUID. Do not force a source checkpoint for every workspace.
3. Create a writable clone into a new generated workspace-generation path. Persist ownership properties and the operation/fencing identity.
4. Install a recovery configuration outside the copied configuration chain. Remove usable upstream connection/slot settings, archive/restore commands, include files, and unapproved preload settings. Keep the clone in standby recovery initially.
5. Start the clone with no externally reachable endpoint and no outbound network access. Use the source-compatible recovery profile, not blindly the small runtime profile.
6. Recover and promote this clone through the host-controlled procedure below. SQL availability in hot standby is not a prerequisite for requesting promotion. Before exposure, verify that recovery completed and the replayed source position satisfies the persisted barrier.
7. Apply the isolation plan while still disconnected: disable copied login authorities, configure fresh workspace roles, disable approved copied jobs/subscriptions, and check privileges. Reject anything outside the manifest.
8. If necessary, cleanly restart with the lower steady-state profile. Recheck read/write readiness and retained isolation configuration.
9. Commit the generation's readiness evidence, then publish its endpoint. Issue credentials only through the authorized credential operation.

Live filesystem snapshots must include the recovery files required by PostgreSQL. The P1 one-dataset restriction avoids pretending separately timed snapshots of data and WAL are atomic. [8]

Before capture, persist the baseline replay position and verified source lineage as required by section 7.3. Start the disconnected clone with local WAL available and no recovery target that can silently truncate the required recovery. Do not gate promotion on `pg_isready`, a SQL connection, or `pg_promote()`: hot-standby query admission can remain unavailable while long-lived transactions with more than 64 subtransactions await additional WAL. Those future records are absent from an immutable capture. A consistent recovery state and permission to execute standby queries are separate conditions. [3]

Use the generation-fenced host helper to request `pg_ctl promote` and let PostgreSQL finish its supported recovery procedure. This must never bypass a missing-WAL or consistency failure. Once SQL becomes available, verify `pg_is_in_recovery() = false` and read `pg_last_wal_replay_lsn()`. The latter remains the last replayed recovery position after promotion; do not substitute the clone's newly generated WAL position. Persist that source-position evidence and validate lineage and lower bound before the optional profile restart, which can clear recovery-function evidence. After restart, check the runtime against the persisted generation/GUID and readiness record. [7][46]

T-23 must reproduce an overflowed-subtransaction snapshot with a still-open source transaction, disconnect the source, and demonstrate either successful independently verified recovery or an explicit supported-source restriction. A timeout caused solely by waiting for standby SQL does not qualify this algorithm. Recovery without SQL and its limits remain an integration gate, not a result established by this RFC.

A recovery deadline failure leaves the generation unexposed and diagnosable. Missing WAL is not repaired with `pg_resetwal`. Do not delete standby control files just to make a failed clone appear writable.

### 8.3 Sanitized-writer baseline sequence

A sanitized baseline is an ordinary PostgreSQL writer, not a physical standby. Briefly stop the apply scheduler between source transactions, verify the applied-source journal, snapshot the dataset, and immediately resume ingestion. Active source writes continue accumulating in the bounded ingestion stream.

Start a clone from this snapshot using normal crash recovery for a primary snapshot. Do not impose the physical-standby signal/promotion sequence on it. Read the protected applied-source journal after recovery, remove all ingestion authority from the clone, perform workspace isolation, and expose only after the same readiness gates.

This distinction is mandatory in the `BaselineKind` interface. A generic `clone_and_promote_everything` implementation is incorrect.

### 8.4 Readiness evidence

The durable readiness record includes workspace generation, snapshot GUID, runtime digest, source epoch/timeline, lower-bound token, recovered/applied position, policy hash, recovery configuration hash, network-isolation version, credential generation, and successful read/write probe time. The probe uses the actual application role against the published database, not only the administrator socket.

The service-owned probe object should be small and outside application schemas. A probe must not call customer-defined functions, trigger business actions, or imply that all application tests passed.

## 9. Storage layout, accounting, and garbage collection

### 9.1 Layout and initial settings

```text
pool/pgws/TENANT/
  baselines/SOURCE/GENERATION       # complete cluster + WAL
  workspaces/WORKSPACE/GENERATION   # writable clone
  retained/...                     # only when explicitly supported

Outside the snapshotted datasets:
  service configuration, secret mounts, host journal, control sockets
```

Use service-generated opaque identifiers. Record both names and immutable ZFS GUIDs. The privileged helper accepts object IDs, resolves paths itself, rejects symlink/path traversal, and refuses unlabeled datasets. Never accept an arbitrary `zfs` command from a control-plane request.

Proposed starting properties are `compression=lz4`, `atime=off`, `dedup=off`, and normal synchronous-write behavior. Benchmark 8 KiB, 16 KiB, and 128 KiB record sizes before freezing the profile. Keep PostgreSQL `fsync` and `full_page_writes` enabled. No performance result obtained by disabling durability qualifies the design.

### 9.2 Sharing and locality

A writable clone initially shares its origin's blocks; later changes and retained versions consume space. A clone is local to a storage pool. Placement MUST consider baseline locality. Moving a baseline to another pool requires data transfer; snapshots do not eliminate network distance. [9]

For scale-out, first add cells and replicate selected baselines to them. Incremental ZFS sends can transfer changes between compatible snapshots, but a new pool still requires an initial baseline transfer and verified receive state. [12] Avoid transparent cross-cell migration in P1.

Never enable cross-tenant deduplication as a shortcut. Shared storage and privacy domains should follow authorization, not coincidental identical content. Encrypted ZFS clones share their origin's key; independent per-workspace cryptographic erasure cannot be promised for shared blocks. [10]

### 9.3 Capacity and billing counters

Measure project physical allocation at a common dataset ancestor, and report logical referenced size separately. Summing 14 clones' referenced sizes does not measure incremental physical storage. Snapshot space attribution also changes as sharing and references change. ZFS exposes `used`, `referenced`, and the `usedby*` breakdown. [10]

The implementation MUST test quota behavior with a 1 TB origin and a much smaller growth allowance. Do not equate `refquota=20G` with '20 GB of new writes on top of any baseline.' P1 uses project-level hard allocation limits plus qualified per-workspace limits and a cell emergency reserve. Document exactly which allocation counter each limit protects.

Snapshots pinned by old workspaces can retain old baseline blocks even when those workspaces are idle. Baseline-history retention is therefore a project cost, not necessarily a particular agent's write cost. Defaults should favor short-lived workspaces, but expiration never silently applies to a explicitly retained database.

### 9.4 Snapshot references and deletion

Create a durable snapshot-reference record and a ZFS hold before relying on a capture. A snapshot may be shared by requests only when source lineage, privacy profile, runtime compatibility, and freshness bounds match. ZFS holds prevent ordinary snapshot destruction until released. [11]

Deletion first revokes routing/credentials, drains or terminates sessions, stops the process, unmounts and destroys the exact generation, and only then releases its snapshot reference/hold. Garbage collection reconciles management references with real clone origins before deleting an orphan. No generic recursive destroy command is exposed to workers.

Failed creates receive a short diagnostic-retention window. The reconciler must recover the case where a snapshot/clone was created but the metadata write failed. Labels, GUIDs, operation IDs, and the host journal identify the object; a human-readable name alone is insufficient.

## 10. Continuous sanitized ingestion

### 10.1 Independent subsystem and threat boundary

Physical WAL cannot simply be edited to replace customer names while preserving PostgreSQL recovery semantics. The sanitized connector constructs a clean target through logical changes. The first load processes the existing approved dataset; subsequent changes are incremental. Source data and source-side credentials remain in the trusted ingestion boundary, not in agent-accessible storage.

Treat sanitization as a versioned data contract, not an unchecked model judgment. A project-trained tiny classifier may propose semantic labels under sections 10.7–10.15, but only a validated policy can authorize transformations. Each approved policy declares included relations, field transformations, relationship groups, excluded content, synthetic fixtures, and unknown-field behavior. The public API selects an eligible baseline; it cannot override the tenant's required privacy profile.

Native logical replication does not replicate DDL, sequence state, or large objects and does not automatically include every PostgreSQL relation type. These omissions require an explicit compatibility policy. [14] Source features outside the supported subset are rejected, not silently omitted.

### 10.2 Initial consistent load

Create a logical slot and an exported consistent snapshot using a qualified connector. Load all included tables under that snapshot while retaining changes from the corresponding stream boundary. Import the approved schema from the same coordinated source version. Logical decoding provides snapshot/stream coordination, but the consumer must use it correctly. [15]

DDL is frozen or coordinated during initial schema capture and load in the first sanitized connector. This is a source onboarding constraint, not a production write freeze. Long-running snapshot reads and retained WAL have source impact; the operator sets a maximum seed duration, rate, and WAL budget. Abort safely rather than retaining unlimited history on production.

Data is transformed before reaching the target's heap, WAL, indexes, logs, or backups. Any temporary raw spool is encrypted, access-restricted, bounded, and deleted under a documented retention policy. A streaming implementation may avoid most raw spooling, but it must still handle transactions larger than its memory budget.

Publish no baseline until the load and stream catch-up are complete and integrity/privacy validation passes. Failed generations are not mixed into a previous successful baseline.

### 10.3 Transactional apply and crash semantics

The proposed applier handles a complete source transaction as one target transaction. It validates schema/policy eligibility, transforms rows deterministically, applies changes, updates the protected applied-source journal, and commits durably. It acknowledges the source only after that durable commit.

The journal's unique identity includes source epoch, timeline where applicable, commit/end position, and policy version. If the applier crashes after target commit but before acknowledging, a replayed transaction is recognized as already applied. A crash before commit leaves no partial visible transaction. The target journal and data must commit together; a separate in-memory checkpoint is insufficient.

No customer triggers, outbound functions, or application jobs may execute in the applier's target session. If an implementation uses `session_replication_role=replica`, it must account for disabled foreign-key triggers and explicitly validate affected relationships before publication. This RFC does not equate 'applied without an exception' with relational correctness.

For P3, support a deliberately narrow subset: ordinary logged tables, supported scalar/JSON types with explicit rules, declared stable row identities, and positive non-cycling sequences. Reject unsupported large objects, foreign relations, materialized-view refresh semantics, two-phase transactions, unsupported generated-column behavior, and unhandled DDL until qualified.

### 10.4 DDL is the release gate

Evaluate pgstream as the initial connector: its project describes PostgreSQL change replication, schema tracking, and transformations. [16] Its transformer documentation also describes configurations where a constraint error can advance a checkpoint after dropping a row; strict failure handling is essential. [17]

Enable strict mode where available, but do not assume that setting alone establishes source-transaction atomicity, consistent seeding, DDL ordering, or crash-safe offsets. The adapter must prove all four. Pin a tested commit/release. If the library exposes only row-level delivery that cannot meet the transaction contract, extend/fork the adapter or restrict the release; do not weaken the contract silently.

In the first sanitized release, allow additive schema changes only when their policy is approved before apply. A new unclassified field blocks publication of later state. For renames, maintain stable field identity in policy metadata. For type changes, drops, partition changes, or data/DDL mixtures not supported by the adapter, stop at the last valid transaction boundary and return a compatibility error.

Never blindly execute a production data-migration script on the target while also applying the script's source row changes. That can apply the migration twice. Schema evolution and transformed row application need one coordinated owner.

### 10.5 Relationships, values, and sequences

Use explicit transformation domains for related identifiers: every foreign-key participant must use the same mapping contract. Cryptographic keys stay in ingestion, outside workspace storage. Unkeyed hashes of predictable emails/phones are not the proposed protection mechanism. Domain size, uniqueness, truncation, and collision behavior must be specified and tested.

For free text and JSON, either provide an approved field-level transformation, replace with valid fixtures, or block publication. 'Null everything' is not acceptable when it breaks required constraints or makes the application unusable. Apply policy to schema comments, function bodies, embedded URLs, and defaults as well as table values where those can expose secrets.

Maintain sequence high-water metadata during initial load and apply. Before exposing a writable branch, initialize supported sequences above the copied key range with their valid increment/bounds. Branch IDs need only avoid conflicts inside that branch; they are not guaranteed globally unique across workspaces. Exact source sequence position is not part of the sanitized contract.

Rebuild derived search/vector artifacts from sanitized inputs where included. Do not import them as presumed-safe opaque blobs. Full validation can run on initial publication or policy change; ordinary incremental transactions validate their changed relationships and fields, avoiding a complete scan after every update.

### 10.6 Policy changes and deletion

A policy hash is immutable within a baseline generation. Changing transformations or keys creates a new sanitized generation and may require reprocessing the affected dataset. Agents cannot relabel existing raw storage as sanitized. Existing workspaces retain old data until access is revoked and the copies are removed or rebuilt.

For the first sanitized connector, adding an included column changes the compiled plan and creates a new generation even when the column is nullable. Before source DDL, an administrator approves a migration intent containing the expected field, type, transform and constraints. After DDL, discovery verifies actual stable field identity and schema fingerprint; only then can the final immutable plan be approved. An intent alone cannot authorize an unknown field. The old applier stops before the unsupported schema boundary and cannot report newer freshness. Requests pinned to the old baseline return a compatibility error if they require later state.

P3 initially rebuilds the candidate from a newly coordinated consistent snapshot and stream boundary under section 10.2. This also fills existing rows under the new column policy. The candidate has separate capacity and source-retention admission; the operator sees the estimated seed duration and temporary storage before activation. If either exceeds the approved budget, defer the transition instead of starting an unbounded rebuild. After catch-up, validate data, constraints, schema fingerprint and policy state, then mark the candidate eligible in one control-plane transaction. Existing snapshots and workspaces retain their original policy identity.

If validation fails, keep the candidate private and the old generation at its last valid boundary. Do not silently satisfy `latest` from that older state. Return the new baseline ID to consumers for future requests; never mutate an existing baseline ID to point to a different policy. Incremental backfill without a full seed is a later optimization requiring its own atomicity and privacy tests. T-27 covers `ADD COLUMN`, concurrent source writes, failed catch-up, and policy revocation during cutover.

Source deletions propagate into the live baseline, but they do not remove the same records from older branches, backups, or derivative artifacts automatically. Maintain a project data-lineage inventory and a separate revocation/deletion workflow. Access revocation can be immediate; physical deletion follows verified reference removal and backup-retention rules. Document these different events.

### 10.7 Decision: train a project-owned tiny classifier

Train the column classifier from scratch on project-owned or explicitly licensed examples. Do not require Jev, GLiNER2, pretrained embeddings, an external inference API, Python, or a GPU in production. The first model is a sparse, 24-class multinomial logistic regression: a learned linear score per class followed by softmax. This is a trained classifier, not a hand-maintained synonym list; schema rules remain an independent conservative signal.

The model proposes what a column contains. The policy compiler decides whether and how it may be transformed. A prediction is never authorization to expose source values, relax an existing policy, or execute SQL. Discovery runs at onboarding, relevant schema changes, and explicit reassessment. Neither row-by-row CDC apply nor workspace creation invokes the classifier.

```text
Metadata + bounded local value profiling
    -> rules + self-trained column classifier
    -> findings, uncertainty and review
    -> validated, immutable transformation plan
    -> deterministic initial-load / CDC transforms
    -> sanitized baseline -> copy-on-write workspaces
```

One trusted discovery worker can serve a tenant's baselines. Fourteen workspaces do not need fourteen model instances. A missing, invalid, or unqualified model leaves manual policy configuration available; it does not enable raw fallback. This design extends P3 without adding a classifier dependency to P1's physical connector.

### 10.8 Labels and the training unit

One labeled example represents one column in one schema context, not one customer row. Record table/column identifiers, PostgreSQL type family, neighboring fields, constraints, bounded profile statistics, semantic label, provenance, and an application-family group. Repeated samples and schema revisions of the same application are related observations, not independent training examples.

Version 1 uses 24 semantic classes, with an additional non-model decision state, `abstain`. The exact ordered labels are pinned in `contracts/classifier/spec.json`; never rely on a training library's default alphabetical ordering.

| Class group | Ordered labels |
| --- | --- |
| Person names | `person_given_name`, `person_family_name`, `person_full_name` |
| Contact and location | `email_address`, `phone_number`, `postal_address`, `postal_code`, `precise_location` |
| Dates, documents and accounts | `birth_date`, `government_id`, `financial_account`, `payment_card` |
| Credentials and identifiers | `credential`, `network_identifier`, `device_identifier`, `person_identifier` |
| Other named content | `organization_name`, `user_handle`, `url` |
| Mixed or unresolved structure | `free_text`, `structured_payload`, `business_identifier`, `business_value`, `other` |

These classes are routing categories, not a complete inventory of sensitive data. `business_value` and `other` do not mean safe: a salary or medical fact could otherwise land there. The compiler requires an explicit action for every included field. Unknown categories and mixed content go to review, replacement of the whole field, or a separately approved scanner.

Examples must distinguish `users.name` from `products.name`, a customer ID from an invoice ID, a stored API credential from a public token counter, and birth dates from ordinary timestamps. Field relationships, not the model, determine whether matching identifiers share a transformation domain. Version 1 qualifies English/common code identifiers only; unsupported language or context requires review. Generator locale is explicit configuration, never inferred ethnicity or gender.

### 10.9 Training corpus, ownership and labeling

Start with a proposed pilot acquisition target of 10,000-30,000 reviewed column-context examples across at least 100 independently sourced application families. The pilot supports manual review and model development; its minimum size cannot qualify automatic acceptance. At the nominal 15% test split, 100 families yield only about 15 held-out families, below the requirement of 30 per enabled class.

Before an automatic-acceptance candidate is trained, freeze a per-class acquisition and split plan. At the nominal split, at least 200 total families are necessary even if every relevant class occurs in every held-out family; rare classes usually need substantially more. The decisive gate is at least 30 represented held-out families for each enabled class, sufficient accepted cases for the precision interval, and independent temperature/threshold calibration groups. Increasing aliases or rows within one family cannot close that gap. Disable automatic acceptance for a class whose evidence plan is unmet. These are acquisition targets and arithmetic constraints, not an existing corpus or measured accuracy.

Accept project-authored synthetic schemas, legally reusable public schema definitions with recorded licenses, and explicitly opted-in customer metadata/profiles. Public availability alone does not establish redistribution rights. Keep customer-private datasets and model artifacts tenant-scoped unless separate consent authorizes contribution to the shared model. Project-owned training code and weights are proposed as Apache-2.0; the corpus manifest records rights separately.

Do not retain raw production values in the shared training corpus. Compute value-shape statistics locally; exclude value tokens, names, emails, exact dates, raw comments and defaults from training exports. Even metadata and aggregates can be confidential. Feature hashing is not anonymization. Restrict access, apply retention, and require explicit authorization before export. Labels corrected in the product enter an opt-in review queue, not immediate online learning.

Human reviewers assign semantic labels using a written guide. Require adjudication for conflicting labels and second review for credentials, government IDs and financial fields. A teacher model is not required and must not become unverified ground truth. Keep the original application-family identifier and provenance through renames, synthetic variants and deduplication. Check near-duplicate schemas before assigning splits.

Begin with a rules-only reference on the same corpus. Include hard negatives, empty/all-null tables, abbreviations, misleading names, opaque IDs, mixed payloads, and out-of-scope examples. Report results on the unresolved-by-rules subset as well as overall; otherwise obvious names can hide a model that adds little useful coverage.

### 10.10 Bounded discovery and the feature contract

Use a read-only discovery identity in the trusted ingestion boundary. Prefer an approved replica when available. Query catalogs once, bind findings to source epoch and schema fingerprint, and profile selected fields together. Do not use a full-table sort, `ORDER BY random()`, or an independent scan for each column.

Proposed defaults are at most 64 sampled rows per relation, 256 returned bytes per value, 8 MiB returned data per relation, two sampling attempts, and a configurable 500 ms statement timeout. These are source-protection limits, not proof of representative sampling. A hard job deadline and cancellation close the connection and record incomplete evidence. Returned-byte limits do not by themselves bound server I/O or TOAST decompression; exclude oversized/opaque types or use separately qualified readers.

PostgreSQL `SYSTEM` samples blocks, while `BERNOULLI` scans the table. The former is a candidate for bounded discovery but can reflect clustering and return no useful rows. `REPEATABLE` only repeats a sample when the table has not changed. [40] Use estimates rather than an exact count to choose sample rates; on insufficient evidence, record partial/none rather than silently treating the field as safe.

The classifier consumes 16,384 hashed metadata features plus 32 fixed numeric features. Metadata includes normalized identifiers, selected neighboring names/types, key roles, and explicit table/column token interactions. Generate namespaced word features and character 2-5-grams after a versioned ASCII camel/snake-case normalization. Non-ASCII identifiers are flagged for review in v1, not silently transliterated into trusted labels. Comments, raw defaults, and row-value tokens are excluded.

The numeric features describe sample availability, lengths, null/empty/distinct fractions, bounded format matches and type/constraint flags. Exact order, denominators, clipping and missing-data behavior live in the companion feature contract. Prefix truncation, incomplete sampling and unsupported types are explicit review flags; missing values are not evidence of absence. For JSON/arrays, v1 classifies the container and requires a path policy or whole-field replacement, not inferred coverage of unknown future paths.

Feature hashing bounds the vector dimension but introduces collisions. [45] Use our own pinned FNV-1a-64 mapping: low 14 bits select the bucket; the high bit supplies the sign. Aggregate duplicate features, L2-normalize the hashed block, then append numeric values in [0,1]. Cap the unique emitted features at 2,048 per column; overflow requires review. This hash is an encoding choice, not a security control.

Implement feature extraction once in Go, shared by the runtime and a `pgws-features` CLI used by training. Python reads its sparse output; do not independently reproduce tokenization with a different hashing library. Golden fixtures must cover normalization, namespace boundaries, collisions, empty input, feature caps and class order. Persist the feature-contract digest with every model.

### 10.11 Training, calibration and validation splits

Use an offline, CPU-capable Python training environment with pinned scikit-learn, NumPy and SciPy versions. Build sparse CSR features from the Go extractor. Fit a multinomial logistic regression with L2 regularization, evaluating the `saga` solver first. scikit-learn documents multinomial optimization and sparse input support; the release must pin tested API parameters rather than use moving defaults. [36]

Partition by application family before augmentation: approximately 65% training, 10% development, 10% calibration and 15% locked test groups. Adjust counts to maintain independent class coverage and record the actual split. Grouped cross-validation is available for development, but group isolation takes priority over perfect class balance. [38] Hold all related repositories, forks, schema revisions and generated variants in the same partition. Fit learned preprocessing and tune regularization only on allowed training/development data. [39]

Compare unweighted loss with capped training-only class weights. Tune regularization on the development groups; treat non-convergence as a failed candidate. Fit one positive temperature T on calibration-set logits by minimizing negative log likelihood. Calibration data must be disjoint from model-fitting data. [37] Reserve a separate group-disjoint portion of calibration data for choosing per-class acceptance thresholds and top-two margins. Do not repeatedly inspect the locked test while tuning.

The deployed calculation is `p = softmax((W*x + b) / T)`. Subtract the largest scaled logit before exponentiation. Export the learned coefficients reordered into the contract's class order, cast to FP32, then fit/check calibration and validate the exported representation. Reject non-finite weights, invalid shapes, missing classes, or non-positive temperature. Compare all output scores against the Python reference using a proposed absolute tolerance of 1e-5; disagreements near decision thresholds cause review, not optimistic acceptance.

For each candidate publish per-class precision/recall, macro-F1, confusion matrices, calibration error, accepted-coverage versus error, and application/language subgroup results. Measure the complete rules-plus-model-plus-policy system separately from the classifier alone. Report uncertainty using application-family cluster resampling; use binomial intervals only with a defensible independent sampling unit. SciPy supplies exact and Wilson proportion intervals, but does not make correlated columns independent. [44]

No model is trained by this RFC update. Accuracy, convergence, CPU requirements and dataset sufficiency remain experiments. If a class lacks evidence, disable automatic acceptance for that class instead of lowering the evidence standard.

### 10.12 Confidence is not permission

The model returns a proposed class, score, top-two margin, evidence flags, schema fingerprint and model digest. Scores are estimates, not guaranteed probabilities that a field is harmless. High scores on unfamiliar inputs can still be wrong. Use hard review conditions for unsupported contexts, conflicting rules, incomplete required evidence, feature overflow, mixed content and unqualified classes.

The precedence is: tenant-approved field policy; mandatory protective rules; eligible model proposal; otherwise review/block. A model must never undo an approved transformation or permit `copy_original`. A deliberate administrator exemption remains explicit, audited and scoped to the current field/schema contract. Approval of a replacement still requires type, relationship and uniqueness validation.

Default operation is review-only. As a proposed later release gate, each class enabled for automatic replacement needs an accepted-case precision lower bound of at least 99% at 95% confidence on held-out application families, with at least 30 represented families and sufficient accepted cases. These are product acceptance targets, not achieved results or an anonymity guarantee. The gate applies to the complete selected path, including rule/model conflicts. If evidence is insufficient, remain review-only.

Also report recall on sensitive fields and the fraction requiring review. A system that blocks everything does not demonstrate useful classification. Seeded raw-pass-through cases, unknown columns and unsupported categories must all block publication in integration tests. Sampling cannot prove absence: with independent samples, a 1% sensitive-value rate and 64 draws gives a miss probability of `0.99^64`, approximately 52.6%. Real clustered sampling can be worse.

### 10.13 Model packaging and the Go runtime

Ship a small data-only model bundle: manifest, FP32 weight matrix, bias vector, calibration scalar, class acceptance configuration, provenance/model card, checksums and a release signature. The matrix is row-major `[24,16416]`; bytes are IEEE-754 little-endian FP32. The weight matrix occupies 1,575,936 bytes (approximately 1.503 MiB), plus 96 bias bytes. These are arithmetic sizes, not process-RAM measurements.

The manifest binds the feature contract, label order, dataset/split digests, trainer revision and runtime compatibility. Thresholds belong to a versioned, approved decision contract. They are not magic universal constants. An unqualified class has automatic acceptance disabled. Training-set identifiers and weights must not inadvertently expose private tenant metadata; private adapters remain private.

Use ordinary Go loops for sparse dot products and softmax. No Python, GPU, cgo, ONNX service or network call is required in the proposed inference path. The built-in qualified bundle may use Go `embed`; the standard library supports embedding build-time files. [42] An administrator may install a signed local bundle. Verify signatures against pinned operator keys, lengths, shapes, finite values, digests and feature compatibility before activation. Reject arbitrary serialized Python objects: pickle-family persistence can execute code when loaded. [41]

Load one immutable model per discovery process, share it across workers, and use bounded scratch buffers. Atomic replacement affects new discovery jobs only; running jobs remain pinned. Missing or invalid model state blocks automatic discovery without invalidating already approved transformation plans. A model update creates new findings, not silent changes to a baseline's policy hash.

Proposed qualification budgets are: model bundle no larger than 4 MiB; model-related resident-memory increase no larger than 32 MiB at eight concurrent inferences; p95 feature extraction plus scoring below 5 ms per bounded in-memory profile on a recorded single CPU core. Source queries, profiling I/O and policy validation are measured separately. These are targets to verify on x86-64 and arm64, not measured performance. Training memory is a separate offline budget.

### 10.14 From labels to stable synthetic data

The compiler maps reviewed semantic categories to allowlisted typed generators. `person_given_name` and `person_family_name` can select names from pinned dictionaries; locale and fixture behavior are configured explicitly. The model does not generate text or SQL and does not run once per row.

Use a stable mapping contract, for example `HMAC(key, encode(domain, entity_id, field_role, generator_version))`, with an unambiguous length-prefixed encoding. Entity-stable mappings create a consistent synthetic identity; value-stable mappings preserve approved equality relationships across tables. A name dictionary is not a uniqueness mechanism. Unique emails/IDs require enough output space, constraint checks and an explicit collision registry or a qualified injective mapping. Truncation cannot silently discard uniqueness.

Keep first/last/full names consistent through a shared entity mapping. Preserve null semantics and required formats; disabled credentials must not authenticate to production. Existing source identifiers may remain only under explicit policy. HMAC-derived output is a deterministic pseudonymization technique, not proof that every individual is anonymous. Keys and any identity/collision registry remain outside agent-accessible storage.

For large initial loads and CDC, compile table/column access once, use bounded batches, and reuse buffers. Honor missing-versus-null values: PostgreSQL logical messages distinguish an unchanged TOAST value from SQL NULL. [43] Fetch required stable identity through the supported replica-identity/lookup contract; missing key material blocks apply rather than producing a different identity. Mapping registry writes and source offsets participate in the transaction/recovery contract of section 10.3.

### 10.15 Integration, drift and rollout

Store each discovery run with source epoch, schema fingerprint, model/feature/rule digests, limits, evidence completeness and status. Store findings by stable field identity with semantic proposal, review flags and decision provenance, but no raw samples in ordinary logs. Approved policies reference the discovery evidence and compiled-plan digest. The current `privacy_policies.policy_document` can hold those references initially; production persistence needs an additive migration and tenant-scoped constraints before P3. No classifier management endpoint is added to the agent lifecycle API.

A proposed admin workflow is `privacy discover`, `privacy review`, `privacy compile`, then `privacy publish`; these are commands to implement, not commands supplied by the current POC. Discovery cannot publish directly. Hash the canonical policy, rules, field identities, mappings, key references and generator versions into the plan. Revalidate schema identity before activation. A rename/type change or new field queues discovery and blocks affected publication until approved.

Keep bounded deterministic guards on the CDC path for incompatible values, unexpected JSON paths and approved format contracts. Guards can trigger reassessment, but do not claim universal sensitive-content detection. An existing allowlisted free-text field does not become safe through periodic sampling. Whole-field fixtures or an independently qualified per-value scanner remain required where the policy demands them.

Roll out a candidate in shadow mode against the current approved policy, then review disagreements. Activation changes future proposals only. Policy changes still create a new baseline generation under section 10.6. Reverting a model does not undo previously exposed data; use lineage-based revocation/rebuild for an actual privacy incident.

Publish the training recipe, label guide, public/consented corpus manifest, split manifest, model card, evaluation report and weights with release provenance. Private training is supported without requiring upload to the SaaS. A customer-facing correction is not permission for cross-tenant training or automatic live retraining.

## 11. Workspace lifecycle and migrations

### 11.1 Desired state versus observed phase

Store desired state as `running`, `paused`, or `deleted`. The logical workspace points to one current generation; keep old and candidate physical generations in a separate table during reset, cleanup, and recovery. Store observed phase separately, for example `queued`, `waiting_for_freshness`, `snapshotting`, `cloning`, `recovering`, `isolating`, `starting`, `ready`, `pausing`, `paused`, `deleting`, `deleted`, `failed`, or `lost`.

A failed operation is not necessarily a failed resource. A rejected resize can leave a ready workspace intact. A failed creation can leave private storage requiring cleanup. The API must expose resource state, operation outcome, and structured error independently.

### 11.2 Pause and resume

Pause revokes admission of new sessions, waits through a documented drain period, terminates remaining sessions when required, and stops PostgreSQL cleanly. Storage and snapshot references remain. Resume starts the same generation, performs recovery if necessary, rechecks policy and credential validity, and republishes its endpoint.

P1 supports explicit resume through API/CLI. No connection-triggered autoscaling claim is made. A later proxy can request resume, but must have bounded wake-up time and correct behavior for client retries, cancellations, and idle sessions.

TTL is an absolute expiration policy; idle suspension is a distinct optional policy. A client connection or open transaction must not indefinitely defeat hard expiration. Long migrations request an explicit expiry extension and wait for successful host installation before starting. Operator overrides are audited.

The host enforces persisted workspace expiry independently of the management database. P1/P2 additionally require a signed serving lease bound to authority epoch, tenant/project, workspace generation, desired revision and host identity. The lease carries an expiry no more than 120 seconds after issuance; renew it every 30 seconds while current authorization remains valid. These are proposed defaults to qualify. Close ingress, terminate existing sessions and stop the runtime at the earlier of workspace expiry and serving-lease expiry. Lease expiry alone retains storage privately for reconciliation; workspace TTL authorizes the recorded deletion workflow. A host restart begins closed and requires a fresh lease.

Install deadlines with a monotonic timer, conservatively accounting for the qualified clock-error bound of at most five seconds. A backward wall-clock adjustment must not extend access. Reject expired/delayed leases and clocks outside the supported bound. Lease or workspace expiry has a proposed five-second maximum enforcement delay; include scheduling delay in qualification. Connected revocation targets five seconds. During a control-plane partition, revocation is bounded by the remaining lease plus clock/enforcement allowance, at most 130 seconds under these defaults. Do not claim immediate remote revocation during partition. An independently supervised host guard must close access if the agent stalls; a shared failure that leaves SQL reachable beyond this bound fails T-24.

The `extend_ttl` action accepts `expected_generation`, `expected_expires_at` and an absolute `expires_at`. Extension only increases expiry and cannot exceed seven days from original workspace creation or a tighter project limit. The API atomically compares generation, previous expiry, desired state and current time, records the requested deadline in the operation with a new desired revision, and then installs that deadline at the host under its fence. Keep the public workspace expires_at at its previous value until installation is acknowledged and the matching revision is committed. If acknowledgement is lost, reconcile the host installation record and its terminal-expiry state before publishing success. An expired workspace or one whose deletion has won cannot be revived. Success is reported only after host acknowledgement; until then clients must assume the previous deadline. Repeating an idempotency key returns the original operation and cannot add more time. A failed installation preserves the old effective deadline. Reconciliation may adopt an installation that the host durably accepted before its old deadline; it must never install an extension retroactively on an expired host. A committed expiry decision is terminal for that workspace identity.

### 11.3 Reset and reproducibility

`reset` requires the expected workspace generation and `discard_local_changes=true`. It creates a new candidate generation from a specified snapshot or fresh baseline. Cut off the old endpoint before destructive handover; never switch an existing transaction to another database. Publish the replacement only after readiness passes. Old credentials cannot authenticate to the new generation.

If replacement fails, preserve the previous generation privately for a bounded recovery window and report the failure. Do not claim the reset succeeded because the old database still runs. The final deletion decision follows the operation journal and current desired state.

Migration artifacts remain in the application repository. The service records the commit SHA, migration manifest hash, baseline fingerprint, runner identity, and test-result references. A baseline's migration-history table helps the normal tool determine pending migrations. Agent-supplied success receipts are informational unless verified by a trusted runner.

To revalidate a change against current production, create a new workspace and replay the reviewed migration/test artifacts. Do not merge arbitrary row edits. `pg_rewind` reconciles a diverged cluster toward a source; it is not a preservation-and-merge mechanism for independent workspace changes. [35]

### 11.4 Durable production databases are a different tier

A disposable workspace may still contain useful uncommitted engineering work. Make its loss/retention policy conspicuous. P1/P2 do not advertise a recovery-point objective for workspace writes after complete cell loss; surviving process restarts and surviving loss of all storage are different guarantees.

A future 'retain as production database' operation must add backup policy, restore drills, deletion protection, availability objectives, operational ownership, and separate pricing. It must not mean 'remove the TTL and hope.' Automatic replacement of an existing production database with an experimental branch is out of scope.

## 12. Control-plane data model

### 12.1 Authoritative records

The companion `contracts/control-plane.sql` is a proposed initial schema, not an already deployed service. It includes tenant/project scoping and the core lineage, operation, credential, and usage records. Production security roles and policies require separate migrations and tests.

| Entity | Important fields and purpose |
| --- | --- |
| `sources` | Tenant/project, connector type, epoch, system ID/timeline, secret reference, status |
| `privacy_policies` | Version/hash, approved policy document, approval and revocation state |
| `baselines` | Source/generation, mode, runtime digest, compatibility manifest, observed position |
| `snapshots` | Baseline, storage GUID, lineage, lower bound, policy hash, reference state |
| `workspaces` | Snapshot, generation, desired/observed state, TTL, profile, endpoint metadata |
| `workspace_generations` | Snapshot, physical identity, runtime/endpoint evidence for each reset or initial creation |
| `operations` | Request hash, idempotency scope/key, expected generation, attempt/lease/fence, outcome |
| `credentials` | Workspace generation, role/secret reference, expiry, revocation; never plaintext |
| `snapshot_refs` | Durable owners of snapshot retention; reconciled against physical origins |
| `audit_events` | Actor, action, target, result, request/operation ID; no customer row payload |
| `usage_events` | Deduplicated interval measurements and dimensions for auditable billing |

Every cross-resource reference is checked in the same tenant/project. Composite foreign keys prevent attaching a workspace to another project's snapshot. The core contract requires a policy ID/hash for every logical-writer baseline and forbids either on physical baselines. Snapshot lineage and policy are copied and checked against the referenced baseline; baseline source identity, kind, runtime and compatibility/privacy contract become immutable on insertion. Updates to those values require a new generation. Privacy-policy content/hash/version are immutable; approval and revocation state remain separately mutable.

The proposed SQL adds enforcement triggers for these immutable fields and snapshot identity checks because nullable raw-policy fields cannot be safely matched by an ordinary nullable composite foreign key alone. It does not enforce external authorization or verify that a supplied hash cryptographically matches a document. The compiler must calculate canonical digests, and publication must lock/recheck the current policy state, actual runtime/GUID, authority epoch, desired revision and generation in the same management transaction that records readiness. Host route installation must carry the matching fence and serving lease. Database owners can bypass database protections; runtime grants remain a separate required migration.

Before P3, add tenant-scoped discovery runs, field findings and qualified-model registrations. Link immutable model/feature/schema digests and approvals through the policy document. These additional persistence migrations are specified in section 10.15 but are not implemented in the companion core SQL. The classifier contracts are internal/admin contracts, not new agent permissions.

### 12.2 Reconciliation and fencing

The scheduler uses short management transactions to claim work. A worker renews a lease during long operations; it does not hold a database transaction open throughout a base backup. The desired state and operation journal are authoritative, not a worker's memory.

Each resource mutation carries a monotonically increasing fencing token. The host stores the highest accepted token durably and serializes mutations for that resource. A stale worker cannot destroy or republish a newer generation. All remote calls include operation ID, expected generation, desired revision, and fence.

Database locks alone cannot prevent a previously partitioned worker from issuing a delayed storage command. The host must enforce fences too. For future host failover, process/volume fencing is also necessary: never mount the same writable generation on two independently active hosts. P1 avoids automatic cross-host failover.

### 12.3 Exactly-once effects, not exactly-once messages

Workers and API clients can retry. Implement idempotent `ensure` operations: ensure snapshot with matching ownership/GUID; ensure clone with expected origin; ensure runtime with expected generation; ensure endpoint not stale. A name collision with different ownership is a hard error, not success.

The control plane records intended work before side effects. The host journal records local start/completion and identity. If a worker crashes between action and metadata commit, reconciliation observes the actual object and adopts only a matching result. Unknown resources are quarantined and surfaced, not automatically destroyed.

### 13.1 API surface

The companion OpenAPI 3.1 document specifies the initial core lifecycle contract. The broader source/policy administration endpoints described here can be implemented incrementally without changing the workspace semantics.

| --- | --- | --- |
| `POST /v1/projects/{project}/sources` | Register an approved source reference | Project administrator |
| `POST /v1/projects/{project}/sources/{source}/barriers` | Issue a signed freshness token | Authorized source/baseline consumer |
| `GET /v1/projects/{project}/baselines` | List eligible baseline generations | Project member/agent |

All writes require an `Idempotency-Key`. Bind it to tenant, project, HTTP method/path, and normalized request hash. Reusing a key with different contents returns `409`. Keep records for a published minimum retention, proposed as seven days for lifecycle writes, then return an explicit expired-key result where duplicate effects would be dangerous.

### 13.2 Workspace request and response

```json
{
  "baseline_id": "22222222-2222-4222-8222-222222222222",
  "task_id": "checkout-migration-42",
  "freshness": {
    "mode": "at_least",

```

The response contains workspace ID, generation, phase, operation ID, and polling information. The endpoint appears only once ready. No request field permits an agent to set a dataset path, container image, source DSN, superuser flag, or disable mandatory sanitization.

Errors include a stable code, retryability, operation ID, and safe detail. Proposed codes include `SOURCE_UNREACHABLE`, `FRESHNESS_TIMEOUT`, `LINEAGE_MISMATCH`, `UNSUPPORTED_SOURCE`, `PRIVACY_POLICY_BLOCKED`, `RECOVERY_FAILED`, `RESOURCE_EXHAUSTED`, `GENERATION_CONFLICT`, `EXPIRY_CONFLICT`, `WORKSPACE_EXPIRED`, `AUTHORITY_RECONCILIATION_REQUIRED`, and `IDEMPOTENCY_CONFLICT`. Do not leak database rows or source passwords in errors.

### 13.3 Credential semantics

Credentials are scoped to one workspace generation and role. Store a secret reference plus expiry/revocation metadata. The plaintext is returned only through the credential operation, with `Cache-Control: no-store`; log only the credential ID. Retried issuance either replays the same encrypted response to the same authenticated scope within its replay window or returns the already-issued credential reference and requires explicit replacement.

A revoked credential cannot create new sessions. Revocation requiring immediate effect also terminates its existing sessions. PostgreSQL password expiry alone does not forcibly end an already established connection; session revocation must be implemented explicitly. Role attributes distinguish login capability and password validity. [24]

### 13.4 CLI and SDK behavior

Proposed commands are `pgws source add`, `pgws baseline status`, `pgws create`, `pgws wait`, `pgws credentials`, `pgws pause`, `pgws resume`, `pgws reset`, `pgws extend --expires-at`, and `pgws delete`. Machine mode returns stable JSON and nonzero exit codes on failure. Waiting supports a caller deadline and cancellation without implicitly deleting a resource.

Provide a small TypeScript and Python lifecycle SDK generated or tested against OpenAPI. Application SQL continues through existing drivers and ORM tools. An MCP adapter may wrap the lifecycle API later; it must not gain broader permissions or expose unrestricted source-query tools.

The agent's instructions should say that a workspace is isolated and may be stale, identify its baseline/privacy mode, explain TTL, and forbid interpreting test success as production approval. This is useful context, not the security boundary.

## 14. Security design

### 14.1 Principals and authorization

Separate tenant administrators, project developers, workspace agents, ingestion workers, host agents, and service operators. A task credential grants create/use/delete rights only within approved resources and budgets. It cannot register sources, approve privacy policies, install arbitrary runtimes, or read another task's secrets.

Service authorization lives in current control-plane state, not in a customer snapshot. Restoring an old workspace cannot restore an old user's service access. Use explicit tenant/project checks for every object lookup and operation, and test all ID substitution paths.

Management PostgreSQL should use separate migration and runtime roles. Row-level security can add defense in depth, but table owners and privileged roles can bypass it; it must not be the only cross-tenant boundary. [25] Transaction-local tenant context must not leak between pooled connections.

### 14.2 Database roles and copied authority

Before exposure, disable copied login credentials and grant only fresh workspace roles. Preserve application ownership through a reviewed ownership mapping, not an indiscriminate grant of all source roles. Source roles with superuser, replication, create-role, bypass-RLS, file/program access, or unsafe memberships are never inherited as agent authority.

A table owner may intentionally bypass its own application row policies during testing; that is distinct from access to production or another workspace. Do not market application RLS inside an owner-writable branch as protection for raw values already present in that branch.

Revoke unapproved access to privileged `SECURITY DEFINER` routines and audit inherited role memberships and default grants before exposure. Disabling LOGIN alone does not remove indirect authority.

Functions, triggers, and extensions are executable input. Source-provided superuser code can be dangerous even if the agent itself receives a restricted role. P1 accepts only reviewed sources and runtime extensions. Public arbitrary imports require the stronger tenant boundary and a dedicated import sandbox. PostgreSQL's extension guidance treats installation privileges and extension scripts as security-sensitive. [23]

### 14.3 Runtime and network requirements

Drop Linux capabilities, use a non-root database UID, read-only root filesystem, bounded tmpfs, process limits, memory/CPU limits, restrictive seccomp/AppArmor or equivalent profiles, and no runtime socket mount. The privileged host helper runs separately and accepts only its typed allowlist.

Deny workspace egress by default, including source networks, management networks, other workspace namespaces, host services, and cloud metadata addresses. Permit only the minimum ingress path for database clients. Validate IPv4, IPv6, DNS, restart, and network-recreation behavior; a Docker `--internal` flag is not a complete threat model.

Database transactions cannot undo external payments or email. Replaced credentials and egress denial are mandatory before user SQL, not optional cleanup after the first query. Approved external integration tests use separate sandbox endpoints and credentials.

### 14.4 Secrets, audit, and deletion

Encrypt storage and backups within each tenant boundary. Protect service secrets using an adapter suitable for self-hosting and managed deployment. Key access follows current authorization; clone access does not include decryption authority for unrelated datasets.

Audit lifecycle requests, policy changes, secret issuance/revocation, source onboarding, operator access, and destructive actions. Avoid query text and row-value logging by default. Customer SQL, object names, and logs may contain injected instructions; control components treat them as untrusted text, never as operational commands.

Deleting a role, passfile, or row does not make a raw physical clone anonymous: old blocks, catalogs, WAL, and backups may retain source information. The physical connector's guarantee is controlled raw access, not sanitization. The sanitized connector avoids placing raw values in agent storage in the first place.

### 14.5 Abuse boundaries

Enforce tenant spend limits, creation rate, queue depth, active instance limits, and hard storage admission. Repeated failed imports must not create unbounded retained files or source slots. Workspace users cannot change cell-level quotas by setting PostgreSQL session parameters.

No anonymous public signup should receive privileged raw imports on shared infrastructure. Hosted beta onboarding remains approved and tenant-dedicated until adversarial testing and incident response are operational.

## 15. PostgreSQL endpoint and session design

### 15.1 Start with a simple endpoint

P1/P2 expose one controlled TCP endpoint/port per workspace generation or a transparent TCP forwarding rule to that instance. Terminate PostgreSQL TLS in the instance using a service-managed certificate. The advertised hostname must match certificate validation; never ask clients to disable verification.

This avoids building a PostgreSQL protocol router before the storage lifecycle is correct. Ports are allocated by the service, not the agent. Stop/reset/delete removes routing and rejects fresh authentication before destroying the runtime.

### 15.2 Later proxy requirements

A multiplexing proxy must handle PostgreSQL SSL negotiation, normal and extended query flow, `COPY`, prepared statements, notifications, streaming results, cancellation, and driver connection parameters. Cancellation uses a separate connection with backend key data, so a naive hostname/SNI router cannot be assumed sufficient. [18]

Do not silently replace session semantics with transaction pooling for migration tools. Session locks, temporary tables, and prepared statements may need session affinity. Qualify clients including `psql`, `pgx`, Psycopg, node-postgres, JDBC, and at least two real migration tools before claiming broad compatibility.

Connection-triggered resume should be implemented only after a bounded queueing/wakeup design, generation-aware cancellation routing, and retry tests. P1 clients call `resume` and wait for readiness explicitly.

## 16. Resource planning: 14 workspaces and a 1 TB baseline

### 16.1 Units and assumptions

Storage examples use decimal TB/GB. Memory profiles use binary GiB/MiB. A '1 TB database' must be measured both as PostgreSQL logical relation size and actual filesystem allocation; compression, indexes, bloat, WAL, and temporary files change the relationship.

The estimates below assume 14 lightly active, independent PostgreSQL instances; a source hosted elsewhere; one baseline; low client concurrency; and no concurrent whole-database rewrite. They are capacity hypotheses, not benchmark results or a hardware purchasing guarantee.

### 16.2 Small steady-state profile

| Setting | Proposed small profile |
| --- | --- |
| Container memory limit | 1 GiB |
| CPU limit | 1 CPU equivalent; not a dedicated core guarantee |
| `shared_buffers` | 256 MiB |
| `work_mem` | 4 MiB |
| `hash_mem_multiplier` | 2 |
| `maintenance_work_mem` | 64 MiB |
| `autovacuum_work_mem` | 32 MiB; one worker initially |
| Connections | 16 server limit; eight application connections |
| Parallel query/maintenance | Disabled in the small profile initially |

The recovery profile may need larger source-compatible settings and memory. Limit simultaneous recoveries and record their peak consumption separately. Following promotion and restart, the small profile applies only if validated for that source/workload.

PostgreSQL memory is not `database_size × workspace_count`. Shared buffers are per instance, while sorts/hashes and concurrent operators can consume additional memory; `work_mem` is not a single per-server allowance. [28] Fourteen 256 MiB buffer pools total 3.5 GiB, already inside their container limits.

### 16.3 Host planning envelope

| Budget item | Light-workload experiment |
| --- | ---: |
| Fourteen 1 GiB workspace limits | 14 GiB |
| Baseline allowance | 2 GiB |
| Host ZFS ARC budget | 8 GiB |
| OS, host agent, recovery burst, spare capacity | 8 GiB |
| Total planning envelope | 32 GiB |

The 8 GiB spare line is not permission to overcommit unlimited recovery jobs. If discovered recovery requirements exceed it, admit fewer concurrent starts or select a larger host. The baseline may also require more than 2 GiB for a high-WAL-rate source. Control-plane services and an on-host synthetic source add their own budgets.

Classifier capacity is not multiplied by the workspace count. The proposed FP32 matrix is approximately 1.503 MiB; allow a separately measured discovery-process budget including buffers and profiling. Section 10.13 sets a 32 MiB model-related RSS target, not a full ingestion-memory claim. Initial sanitized loads, source transactions and offline training need separate memory limits. No additional RAM figure is included in the 32 GiB host estimate without measurement.

Use 32 GiB as the light-workload experiment, then test a 64 GiB envelope and larger per-workspace profiles for parallel migrations. Keep hardware, workload, concurrency, and cache conditions recorded so the comparison is meaningful. No fixed host RAM amount guarantees acceptable scans of a 1 TB working set.

Linux cgroup v2 exposes memory usage/events and CPU controls; host pressure must still be observed independently. [19] OpenZFS exposes ARC sizing controls; set a deliberate tested cache budget instead of assuming the host cache is inside each container's memory limit. [13]

### 16.4 Disk model and amplification

```text
S_total = current_baseline
        + retained_old_baseline_blocks
        + sum(workspace_private_blocks)
        + WAL_and_temporary_allocations
        + metadata_and_operating_headroom
```

At 1,000 GB baseline plus 14 workspaces allocating 10 GB each, the subtotal is 1,140 GB before history/WAL/headroom. At 100 GB per workspace it is 2,400 GB. These examples deliberately do not assume that '1% of rows changed' equals '1% of disk changed.'

A read-heavy workspace can still allocate blocks through hint-bit updates and maintenance, and old captures pin blocks changed by the baseline. [3] Table/index rewrites are particularly important: PostgreSQL distinguishes metadata-only changes from operations that rewrite table/index contents. [29]

Temporary files, failed index builds, autovacuum, and WAL count toward real pressure. Benchmark the exact migration tool and representative schema, not only synthetic point reads. ZFS block sharing is not the same thing as memory sharing, and is not a guarantee of zero I/O.

### 16.5 Capacity-control policy

Proposed cell thresholds: warn at 70% allocated capacity; stop new workspace admission at 80%; shed or pause eligible ephemeral writers before 90%, preserving an explicit ingestion/recovery reserve. These are starting policy values, not universal filesystem recommendations. Tune from measured allocation spikes and reclaim latency.

At an approaching hard limit, revoke new writes before attempting cleanup. Distinguish quota exhaustion from source lag and host loss. Never automatically destroy a retained workspace or an unidentified snapshot to make the dashboard green.

Model seed time as `bytes / minimum effective source-read, network, and target-write throughput`, plus validation and recovery. Model branch readiness separately: queue + freshness wait + snapshot + clone + recovery + isolation + endpoint. A cheap snapshot does not imply instant usable SQL.

## 17. Observability and performance qualification

### 17.1 Metrics

Record lifecycle duration by phase and outcome; queue depth; source receive/replay/apply lag; last successful source observation; baseline compatibility status; active/recovering/paused workspaces; memory current/peak/OOM; CPU throttling; storage allocation and snapshot age; pool free capacity; slot WAL retention; and credential/revocation events.

Track project and cell dimensions in metrics, but avoid unbounded per-query labels. Use workspace IDs in traces/logs where necessary. Query text and source row values are excluded by default. PostgreSQL statistics views provide replication and activity information, but their interpretation must distinguish replay, user queries, and idle sources. [30]

Record privacy discovery duration, sample bytes, incomplete profiles, model/feature digests, per-class proposals, abstentions, rule conflicts, review burden, policy compile failures and publication blocks. Track model-related RSS, extraction/scoring latency and model load failures separately from source I/O. Use bounded-cardinality metric labels; customer schema names and values belong only in authorized records. Report zero classifier calls during ordinary CDC apply and workspace creation as an architectural assertion to test.

### 17.2 Candidate service objectives

| Objective | Candidate target and qualification |
| --- | --- |
| Lifecycle API acknowledgment | p95 below 500 ms when management dependencies are healthy |
| Freshness admission | Never silently violate the selected freshness mode |
| Warm local ready time | p95 below 15 seconds on the published small-workload rig; excluding initial seed |
| Fourteen-request burst | p95 below 60 seconds on the declared rig with bounded startup concurrency |
| Source lag | Meet a published WAL-rate envelope; initial target below five seconds in steady state |
| Control-plane availability | 99.9% target only after operational qualification, not an alpha SLA |
| Workspace durability | Local crash recovery tested; cell-loss writes not guaranteed for ephemeral tier |

These are engineering targets to accept, reject, or revise using measurements. Recovery-setting restarts, large WAL catch-up, cold caches, and source unavailability must be reported, not filtered out to advertise a fast median.

### 17.3 Benchmark matrix

Run 1, 4, 14, and 28 workspaces; 1/2/8 clients each; small, medium, and approximately 1 TB allocated datasets; warm and cold-cache conditions. Record actual physical allocation, not a sparse file nominally sized to 1 TB. Include the source on a separate machine for source-impact tests.

Workloads cover point reads, indexed joins, writes, scans exceeding memory, sort/hash spills, metadata-only migrations, concurrent index builds, table rewrites, rollback/failed migrations, source DDL while branches start, and rapid create/delete cycles. Run source WAL at several controlled rates and include a long-running source transaction.

Report ready-time and query-latency percentiles, errors, failed operations, OOMs, throughput, source slowdown, allocated bytes, retained-history growth, and cost inputs. Keep failed and timed-out runs in the report. Use unique random data where needed to avoid obtaining unrealistic compression savings from repetitive synthetic payloads.

The existing POC's `create-many` is sequential while its `pgbench` phase is concurrent. A real burst test must add concurrent creation rather than mislabel the existing command. [P0]

## 18. Failure handling and recovery runbooks

| Failure | Immediate action | Recovery and user-visible contract |
| --- | --- | --- |
| Source unavailable | Stop issuing `latest` barriers; keep existing workspaces independent | Reconnect; report explicit stale/unavailable baseline, never fake freshness |
| Source slot approaching budget | Alert; stop admission; apply approved source-protection policy | Release/reseed this connector if necessary; preserve production first |
| Recovery missing WAL | Keep clone private; mark recoverable or terminal failure | Recreate from a later valid capture or reseed baseline; never reset WAL blindly |
| Source lineage changes | Freeze new captures/tokens | Verify ancestry or create new epoch; old workspaces remain identifiable |
| Worker crashes | Lease expires; do not assume side effects failed | Reconcile journal/GUIDs and continue with a new fencing token |
| Control plane unavailable | No new mutations or lease renewals; existing SQL works only until its local expiry/lease deadline | Host guard closes ingress and sessions; restore management and reauthorize before reopening |
| Runtime OOM | Record event; remove misleading readiness | Restart under approved policy or request a larger profile; preserve failure evidence |
| Pool pressure | Reject creation and contain writers | Release verified eligible references; never recursively erase arbitrary objects |
| Host reboot | Keep routing closed until reconciliation | Discover datasets/processes, recover instances, revalidate generations |
| Cell/storage loss | Mark affected ephemeral workspaces `lost` | Recreate from source/baseline; no claim to recover unique branch writes |
| Sanitizer uncertainty | Stop apply/publication at last valid boundary | Fix policy/adapter or rebuild generation; no skipped-row success |
| Compromised credential | Revoke, terminate sessions, rotate affected secrets | Audit access and scope; rebuild/sanitize as appropriate |

### 18.1 Management backup and restore

Back up the management database independently with encrypted off-host storage and a tested restore procedure. Proposed beta targets are management RPO at most five minutes and RTO at most one hour; qualify them in drills before treating them as commitments. Keep audit retention and restore-point tracking independent of customer workspace snapshots.

After management restore, do not immediately replay stale delete/create jobs. Reconcile current host fences, resource GUIDs, credential revocations, and operator actions first. Host fencing alone cannot prevent stale authorization from creating a new resource. The first beta therefore chooses fail-closed authorization recovery instead of relying on a revocation journal that has not been designed.

Every restore must start through an operator-controlled recovery entrypoint with a fresh random authority epoch and signing key supplied outside the restored management database. The normal service cannot start against a restored database using the previous authority configuration. Readiness and credential issuance remain blocked. Revoke old service tokens and rotate/disable database login authorities before reopening each generation. Source onboarding, privacy approval, lifecycle mutations and serving-lease renewals remain disabled while reconciliation is incomplete.

Operators reconcile identity-provider membership, task grants and policy decisions using current authoritative records or explicit reapproval. Restored active grants and approved policies are untrusted until that step completes. Preserve a record of which grants and policies were reapproved under the new epoch. Offline cells receive no new leases, expire their old leases within section 11.2's bound, and must acknowledge the new epoch before admission. Pending old-epoch operations cannot execute, including creates and credential issuance for resources that did not previously exist.

Reconstruct fences above each host's durable high-water mark and reconcile exact GUIDs before any destructive work. The beta management RTO includes this manual authorization recovery and must be measured accordingly; it is not a promise that a five-minute-old database backup alone restores safe operation. T-25 restores a backup from before a policy/user revocation and verifies that neither old resources nor newly requested workspaces regain access without explicit reapproval. A future independent revocation ledger may reduce this recovery cost, but is not required by this design.

### 18.2 Baseline and workspace backup scope

A baseline can normally be rebuilt from the source, subject to transfer time and permissions. An optional off-host baseline snapshot reduces recovery time but needs lineage verification. ZFS replication preserves storage state; it does not establish a business-level freshness promise by itself.

Ephemeral workspace snapshots on the same pool are not independent backups. A retained-database tier must define and test off-host backup, WAL/archive organization, and restoration. Physically cloned PostgreSQL systems can share system identifiers and independently produce similar timeline/WAL names; archive namespaces MUST include service workspace ID and generation, not rely only on PostgreSQL identifiers.

### 18.3 Upgrades

Pin runtime, PostgreSQL, OpenZFS, kernel, and extension versions. Canary minor updates with clone/restart/crash tests and an explicit rollback path. Do not mutate the source's major version through this service. A source major upgrade creates a newly qualified generation; old workspaces continue on their pinned runtime until expiry or controlled migration.

Upgrade the host agent and helper with protocol-version compatibility. A schema migration for management metadata must not require simultaneous replacement of every host. Use additive fields and explicit capability negotiation first.

### 19.2 Fault-injection campaign

Inject termination after each lifecycle side effect and before/after each metadata commit. Simulate duplicated requests, lost responses, delayed old workers, host-agent restarts, stale routing, network partitions, source credential rotation, and backup restoration of old metadata. Repeatedly reconcile until the system reaches the declared desired state or a diagnosable terminal state.

Test long source transactions, simultaneous DDL, replication setting increases, exhausted connection limits, invalid extension inventory, corrupt backup manifests, and missing WAL segments. Do not repair test fixtures with unsupported low-level recovery commands merely to get a passing run.

### 19.3 Security acceptance

Before hosted beta: independent review of tenant isolation, source onboarding/SSRF, privileged-helper API, secret handling, and destructive-operation fencing. Test from a malicious database-owner perspective within a workspace and from a malicious source-schema perspective within the allowed source boundary.

No passing checklist establishes universal security. Publish supported roles, permitted extensions, deployment isolation, denied capabilities, and residual risks. Any claim of hostile cross-tenant safety requires its own threat model and review beyond the dedicated-cell design.

### 19.4 Go/no-go gates

P1 requires T-01 through T-10, T-23/T-24/T-26/T-28/T-29, plus source compatibility and restart tests on the pinned stack. P2 adds T-11/T-12/T-25, restore drills, metering reconciliation, incident response, and a documented loss policy. P3 requires T-13 through T-15, T-17 through T-22, T-27, the logical-policy cases of T-29, and a complete supported-schema matrix. A manual-policy P3 alpha may precede qualified automatic classification, but must label auto-discovery as unavailable/review-only and preserve every publication safeguard. Performance marketing for the 1 TB case requires T-16; unit tests are not a substitute.

The team may release a clearly labeled smaller alpha before the full 1 TB experiment, but must not claim that workload is qualified. A privacy failure, false-ready state, cross-workspace write, or destructive stale-worker race blocks release regardless of latency performance.

Do not expose a general plugin interface before the first backend is correct. Keep small internal interfaces for `SourceConnector`, `StorageBackend`, `RuntimeManager`, and `SecretStore`, with capability checks rather than assumed feature parity.

## 21. Open-source distribution and SaaS economics

### 21.1 Licensing and self-hosting

Keep the API, host agent, storage adapter, policy engine, and security-critical lifecycle code available under the project's chosen open-source license. Apache-2.0 is proposed for project-owned code. It allows redistribution and modification subject to its conditions; a competing hosted service is not excluded by the product's open-source promise. [31]

Do not relabel third-party components as Apache-2.0. Maintain a dependency/license manifest, notices, source provenance, and a software bill of materials. OpenZFS documents its own licensing; distribution of the complete system must respect upstream terms. [32] Obtain appropriate licensing review before shipping packaged images or distribution integrations.

A self-hosted operator should be able to run the same core security and isolation controls without buying the SaaS. Sell operation and service commitments, not a closed fix for a safety defect in the public edition.

### 21.2 Proposed commercial unit

Charge for baseline retention/ingestion, provisioned active compute time, additional physical storage/retention, transfer, and support/service level. A workspace can be paused without paying for an always-running instance, while retained storage remains billable. Do not use the number of 'AI agents' as the primary infrastructure meter.

Use project-level shared-baseline/history allocation plus workspace-private allocation as the initial storage model. Explain that an old workspace can retain shared history even without writes. Do not bill 14 TB merely because fourteen clones each reference a 1 TB dataset.

An auditable unit-economics model is:

```text
project cost = baseline compute + baseline/history storage
             + sum(active profile duration × internal compute rate)
             + private storage + data transfer
             + backup/observability/control-plane allocation
             + support and incident allowance
```

Provider prices are deliberately not hard-coded in this RFC. Measure the deployment actually used. Include recovery bursts, initial imports, failed creations, high-WAL sources, and abuse limits; a cheap empty clone is not the whole cost of the workflow.

### 21.3 Demand validation

Start with teams whose agents or CI repeatedly need production-shaped databases for migrations, bug reproduction, or integration tests. Measure completed tasks, time saved compared with their current setup, refresh/reset frequency, retained-workspace age, and willingness to grant source access.

The product must justify both its operational footprint and the trust required for ingestion. A dedicated-tenant first deployment costs more than maximum-density shared hosting, but buys a narrower initial security problem. Revisit density only after evidence establishes that it is the dominant business constraint.

## 22. Risks, alternatives, and unresolved decisions

### 22.1 Risk register

| Risk | Consequence | Mitigation / release decision |
| --- | --- | --- |
| Source cannot expose physical replication | Initial connector cannot onboard it | Publish exact supported sources; qualify logical adapter separately |
| High source recovery settings | Small clones fail or require more RAM | Manifest, temporary profile, bounded concurrent recovery |
| Heavy writes/rewrites | Copy-on-write savings diminish | Growth budgets, TTL, realistic benchmarks, explicit pricing |
| Long-lived snapshots | Baseline history consumes pool | Retention visibility, project budget, bounded default TTL |
| Unordered or partial logical apply | Sanitized data is inconsistent | Transactional journal, DDL gates, crash tests |
| Raw values leak through schema/derived data | Privacy promise fails | Clean target, full policy surface, fail-closed publication |
| Stale worker or restored metadata | Wrong resource is deleted/exposed | Durable host fences, generation checks, reconciliation |
| Source WAL retention runs away | Production outage risk | Customer-approved bounds, alerts, slot ownership, reseed policy |
| Local storage host loss | Unique branch writes are lost | Explicit ephemeral contract; separate future durable tier |
| Imported code escapes SQL assumptions | Host or source exposure | Dedicated cells, allowlisted imports/extensions, egress denial |
| New engine/proxy built too early | Scope expands before core validation | Standard PostgreSQL and direct endpoints first |

### 22.2 Alternatives considered

Logical export/restore per workspace is simple but fails the desired refresh cost model. Keep full import for initial synchronization or exceptional rebuild, not the hot path.

One shared PostgreSQL instance with many databases may reduce process overhead, but shares instance configuration, failure, and privileged execution surfaces. PostgreSQL 18 provides a filesystem-assisted clone option for its file-copy mechanism; platform-dependent storage sharing does not provide the separate-instance boundary chosen here. [33] It remains a local/trusted-team experiment, not the hosted reference design.

A custom branch-aware remote storage engine could improve sharing across compute hosts, but requires a separate storage/recovery project. A filesystem clone backend is chosen to validate the workflow first. Automatic data merge is rejected because storage-level conflicts do not encode business invariants.

The tiny classifier introduces dataset bias, unrecognized categories, correlated-test inflation and misleading confidence. Keep its output non-authoritative, hold out whole application families, measure unresolved cases, and never treat unrecognized content as safe. A smaller model is the initial engineering choice, not a commitment to accuracy before training. A larger candidate needs a separate measured benefit and must preserve the same policy boundary.

### 22.3 Decisions to settle through implementation evidence

The RFC proposes defaults but leaves these evidence-dependent: minimum supported host/kernel/OpenZFS versions; record size and ARC budget; exact small/recovery profiles; eligible extension set; pgstream adapter acceptance; source-provider matrix; retention defaults; and whether demand requires a durable database tier.

The first experiments should resolve the recovery correctness path and source-memory constraints before claiming a latency advantage. The sanitized connector should be stopped from launch if transaction atomicity or DDL/privacy ordering remains uncertain, even if the raw connector is ready.

### Final acceptance statement

The project is ready for its intended first users when an authorized agent can obtain a fresh-enough, independently writable PostgreSQL workspace; run normal migrations and tests; survive supported process/host restarts; and release the workspace without harming production or another task. Every exposure must have recorded lineage, current authorization, isolation evidence, and an enforceable resource budget.

The implementation succeeds by making that contract reliable. It does not need a new SQL dialect, a new query optimizer, or a promise that arbitrary divergent databases can merge automatically.

## Appendix A. Typed implementation interfaces

The following Go is architectural pseudocode. The interfaces specify responsibilities, not a completed library. Implementations must propagate context deadlines, classify retryability, and avoid placing secrets in errors.

```go
type BaselineKind string
const (
    PhysicalStandby BaselineKind = "physical_standby"
    LogicalWriter   BaselineKind = "logical_writer"
)

type Fence struct {
    OperationID string
    Generation  int64
    Token       int64
}

type StorageBackend interface {
    EnsureSnapshot(ctx context.Context, f Fence,
        baselineID, snapshotID string) (Snapshot, error)
    EnsureClone(ctx context.Context, f Fence,
        snapshot Snapshot, workspaceID string) (Volume, error)
    Inspect(ctx context.Context, volumeID string) (Volume, error)
    DestroyGeneration(ctx context.Context, f Fence,
        workspaceID string) error
}

type SourceConnector interface {
    Discover(ctx context.Context, sourceID string) (Manifest, error)
    IssueBarrier(ctx context.Context, sourceID string) (Barrier, error)
    WaitApplied(ctx context.Context, baselineID string,
        barrier Barrier) error
}

type RuntimeManager interface {
    Recover(ctx context.Context, f Fence, volume Volume,
        kind BaselineKind, barrier Barrier) (Evidence, error)
    Isolate(ctx context.Context, f Fence,
        workspaceID string) (Evidence, error)
    EnsureReady(ctx context.Context, f Fence,
        workspaceID string) (Endpoint, error)
    Stop(ctx context.Context, f Fence, workspaceID string) error
}
```

Each `Ensure*` checks an existing resource's identity and origin; it must not merely ignore 'already exists.' Cancellation stops waiting or starts a recorded compensation operation. It must not invoke an unscoped deferred cleanup that can remove a newer generation.

## Appendix B. Operation journal sketch

```text
Claim operation in short management transaction:
  lock eligible operation and workspace
  check desired generation and current authorization
  increment resource fencing token
  set lease owner/deadline and attempt
  commit

For each durable step:
  renew lease; verify desired revision
  invoke typed host operation with fence
  host serializes resource; checks persisted highest token
  host records intent; performs/observes side effect
  host records result and GUID; returns safe evidence
  worker commits step result with generation/fence check

Before publishing endpoint:
  recheck tenant policy, expiry, desired state, generation
  persist readiness evidence
  publish generation-specific route
  mark operation successful

After crash or timeout:
  next worker reconciles metadata + host journal + real objects
  adopt only matching evidence; otherwise quarantine/fail
```

If a policy revocation or deletion wins the final race, the candidate may have finished recovery but still must not be exposed. Routing reconciliation must remove a late stale route even if its creation response was lost.

## Appendix C. Production-readiness checklist

The release owner records evidence links and sign-off, rather than ticking these from design intent:

- Source connector and initial seed tested on the exact supported stack; source resource impact measured.
- Snapshot/recovery and fourteen-workspace workload executed, with failures included in results.
- Cross-workspace and tenant isolation, source egress denial, credential revocation, and imported-code constraints reviewed.
- Operation idempotency, host fencing, reset/delete races, GC, and management-restore reconciliation tested.
- Source WAL budget, pool-pressure policy, monitoring, incident response, and off-host management restore exercised.
- Public support matrix, retention/loss contract, license/dependency notices, and metering semantics published.
- Sanitized mode either qualified separately or explicitly unavailable; no implied anonymization of raw copies.
